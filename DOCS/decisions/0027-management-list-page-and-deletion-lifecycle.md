# ADR-0027: قالب یکپارچه‌ی فهرست پنل‌های مدیریت و مرز چرخه‌ی حذف

- تاریخ: ۲۰۲۶-۱۰-۱۴
- وضعیت: accepted
- تصمیم‌گیرنده: مالک محصول و معماری Funtino

## مسئله و زمینه

فهرست‌های `system-web` و `operations-web` رفتار و نمایش پراکنده‌ای دارند. الگوی مشترک باید عملیات فهرست، فیلتر، وضعیت‌ها و صفحه‌بندی را یکدست کند، بی‌آنکه query، scope یا مجوز سرویس‌ها را به کامپوننت عمومی منتقل کند. همچنین درخواست زباله‌دان شامل آزادسازی کلید یکتا و خارج‌کردن رکورد از همه‌ی مسیرهای دامنه است و صرفاً تصمیم نمایشی نیست.

## گزینه‌های بررسی‌شده

1. پیاده‌سازی toolbar، فیلتر و صفحه‌بندی جداگانه در هر feature؛ تکرار و ناسازگاری را حفظ می‌کند.
2. ساخت کامپوننت مشترک per-app برای فهرست و نگه‌داشتن query و mutation در feature مالک؛ انتخاب‌شده.
3. نمایش زباله‌دان و حذف نهایی با پنهان‌کردن محلی در UI؛ بدون قرارداد مالک داده و اثر قابل‌اعتماد بر ارجاع‌ها/کلید یکتا نیست.

## تصمیم نهایی

- هر دو پنل کامپوننت فهرست مستقل در shell خود دارند. همه‌ی فهرست‌های مدیریتی از همان قرارداد تجربه‌ی بخش ۴.۱ `DOCS/ImplementationRules.md` تبعیت می‌کنند؛ پیاده‌سازی عمومی مجوز، query، scope، عملیات یا مدل دامنه ندارد.
- ایجاد و ویرایش در route صفحه‌ی جدا انجام می‌شود؛ جزئیات route جدا دارد اگر داده‌ی مجاز از endpoint یا فهرست همان API قابل‌دریافت باشد. فیلدهای جست‌وجو و فیلتر در dialog/drawer خود فهرست هستند.
- صفحه‌بندی دقیقاً از قرارداد API استفاده می‌کند. تاریخچه‌ی cursor می‌تواند صفحه‌ی قبلی را بازیابی کند؛ UI کل، ترتیب یا عملیات گروهی‌ای را که API نمی‌دهد جعل نمی‌کند.
- قراردادهای فعلی برای سازمان/شعبه، کارکنان، نقش/دسترسی، فرم، خانواده و audit lifecycleهای متفاوتی مانند suspend، revoke، archive یا read-only دارند. API عمومی زباله‌دان شامل archive-to-trash، restore، permanent-hide، یا آزادکردن شماره/کلید یکتا در قراردادهای موجود یافت نشد.
- بنابراین UI فعلی نباید زباله‌دان یا حذف دائمی نمایشی بسازد و هیچ lifecycle موجودی به‌عنوان حذف تعبیر نمی‌شود. اضافه‌شدن زباله‌دان فقط پس از تصمیم و قرارداد نسخه‌دار در مالک هر داده، migration موردنیاز، حفظ audit/ارجاع‌ها، آزمون idempotency و اثبات عدم اثر دامنه‌ای ممکن است. «حذف از زباله‌دان» نیز داده را فیزیکی پاک نمی‌کند و برای آزادسازی کلید یکتا باید مالک داده جداگانه تضمین دهد.
- این ADR تغییر API یا دیتابیس را مجاز نمی‌کند؛ lifecycleهای فعلی و کنترل‌های server-side بدون تغییر می‌مانند.

## پیامدها و trade-offها

- ابزارها و صفحه‌بندی در هر پنل یکپارچه می‌شوند اما دو پیاده‌سازی app-scoped باقی می‌مانند تا مرز محصول حفظ شود.
- برخی فهرست‌های read-only یا endpointهای بدون pagination دکمه‌ی pagination مصنوعی نمی‌گیرند؛ فقط همان endpoint یا صفحه‌بندی محلی روی مجموعه‌ی کامل مجاز است.
- نبود قرارداد trash به‌صورت محدودیت شفاف گزارش می‌شود؛ کاربر نمی‌تواند از UI وعده‌ی lifecycleای ببیند که backend اجرا نمی‌کند.

## بسترها و سرویس‌های اثرپذیرفته

- `system-web` و `operations-web` از نظر قواعد UI/UX فهرست.
- در حال حاضر هیچ تغییر سرویس، endpoint، schema، migration، مجوز یا آیتم Runflare در این تصمیم وجود ندارد.

## برنامه‌ی migration یا rollback

- کامپوننت per-app به‌تدریج در فهرست‌های موجود استفاده می‌شود؛ در صورت اشکال، feature می‌تواند به الگوی قبلی بازگردد بدون تغییر داده یا قرارداد.
- زباله‌دان به migration داده و قرارداد lifecycle نیاز دارد و در این ADR پیاده‌سازی نشده است.
