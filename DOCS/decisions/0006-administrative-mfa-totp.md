# ADR-0006: MFA مدیران با TOTP و تأیید مجدد نشست

- تاریخ: 2026-09-30
- وضعیت: پذیرفته‌شده
- تصمیم‌گیر: مالک محصول

## مسئله

ADR-0005 ایجاد نقش‌ها، عضویت کارکنان، override و عملیات مدیریتی حساس را به MFA و تأیید مجدد وابسته می‌کند، اما نوع عامل، عمر اثبات و بازیابی حساب تعیین نشده بود. تا تعیین این موارد، عملیات حساس باید fail-closed بماند.

## تصمیم

- عامل دوم مدیران TOTP سازگار با RFC 6238 است: کد ۶ رقمی، بازه ۳۰ ثانیه و حداکثر یک بازه‌ی زمانی خطا در هر طرف. هر بازه فقط یک بار پذیرفته می‌شود.
- کد OTP ورود، به‌تنهایی اثبات MFA یا تأیید مجدد نیست. اثبات MFA فقط پس از اعتبارسنجی عامل در Identity & Access ثبت و به شناسه‌ی نشست سمت‌سرور Gateway متصل می‌شود.
- تازگی اثبات برای مجوزهای `stepUp` حداکثر ۳۰۰ ثانیه است. timestamp، نسخه‌ی عامل و روش اثبات از مرورگر پذیرفته نمی‌شوند؛ Gateway آن‌ها را از نشست ذخیره‌شده به ارتباط داخلی می‌فرستد و IAM نسخه‌ی فعلی عامل را دوباره بررسی می‌کند.
- پس از فعال‌سازی و هنگام بازتولید، دقیقاً ۱۰ کد بازیابی تصادفی، یک‌بارمصرف و پرآنتروپی صادر می‌شود. فقط hash کدها نگه‌داری می‌شود؛ متن کدها فقط همان لحظه نمایش داده می‌شود. بازتولید، کدهای قبلی را باطل می‌کند. مصرف کد بازیابی می‌تواند تأیید مجدد ایجاد کند و در audit ثبت می‌شود.
- secret TOTP در پایگاه داده با AES-256-GCM رمز می‌شود. کلیدها فقط secret زمان اجرا هستند؛ keyring نسخه‌دار برای rollout چرخش آینده در نظر گرفته شده است. در این انتشار re-encryption خودکار credentialها وجود ندارد؛ تا اجرای migration ابزارمند، هیچ نسخه‌ی کلیدی را حذف نکنید. نبودن کلید فعال، مقدار نامعتبر یا نبودن نسخه‌ی لازم باید MFA را fail-closed کند. کلید و secret هرگز log نمی‌شوند.
- رمز، کد TOTP، secret، recovery code و hash آن‌ها در audit، event، telemetry یا خطای عمومی ثبت نمی‌شوند. رخدادهای امنیتی MFA در جدول append-only مستقل ثبت می‌شوند؛ این رخدادها policy role را تغییر نمی‌دهند.
- تلاش ناموفق مشترک TOTP/recovery پس از ۵ بار، حساب MFA را ۱۵ دقیقه قفل می‌کند. پاسخ‌های ناموفق نباید وجود یا وضعیت عامل را افشا کنند.
- وضعیت اولیه‌ی عامل برای هر کاربر خاموش است. راه‌اندازی اولین system admin همچنان فقط با bootstrap خارج از endpoint عمومی، MFA و runbook ممیزی‌شده مجاز است. endpoint عمومی یا مسیر recovery بدون احراز مجدد برای reset عامل وجود ندارد.

## مالکیت و مرز اعتماد

- Identity & Access مالک secret رمز‌شده، کدهای بازیابی، وضعیت/نسخه‌ی عامل و audit آن است.
- API Gateway تنها BFF عمومی است و نشست معتبر را به IAM معرفی می‌کند؛ مرورگر هرگز API داخلی IAM را فراخوانی نمی‌کند.
- Gateway مالک وضعیت تأیید مجدد در هر نشست است. نسخه‌ی عامل در IAM هنگام هر authorization بررسی می‌شود تا نشست‌های قدیمی بعد از disable یا rotate معتبر نمانند.
- `system-web` فقط مدیریت عاملِ حساب احراز‌شده را ارائه می‌کند؛ این صفحه به‌تنهایی مجوز مدیریتی نمی‌دهد. هر عملیات دامنه همچنان نیازمند authorization سمت سرور و scope است.

## پیامدها و محدودیت‌ها

- مهاجرت دیتابیس Identity & Access و Gateway جداگانه، نسخه‌دار و پیش از انتشار app اجرا می‌شوند.
- از دست‌رفتن کامل keyring می‌تواند secretهای موجود را غیرقابل‌بازیابی کند؛ نگه‌داری امن و backup آزموده‌شده‌ی کلید الزامی است. rotation تولیدی تا افزودن migration ابزارمندِ re-encryption ممنوع است.
- انتشار عملیاتی تا زمان تعیین deployment مستقل برای Identity & Access، پیکربندی keyring، دامنه‌ی cookie و CORS، و bootstrap امن مدیر متوقف می‌ماند.
- writeهای IAM در nonproduction و محدودیت fail-closed برای scope tenant در production مطابق [ADR-0008](0008-iam-management-write-gates.md) است؛ تکمیل owner سازمان/شعبه همچنان پیش‌شرط write tenant در production است.
