# ADR-0014: MFA در هر ورود مدیر سامانه و پایان نشست بیکار

- تاریخ: 2026-10-01
- وضعیت: superseded by ADR-0020 for session duration/idle policy and ADR-0025 for per-login MFA
- تصمیم‌گیر: مالک محصول
- دامنه: Identity & Access، API Gateway، Operations Web و System Web

## مسئله و زمینه

ADR-0011 عمر مطلق نشست ۳۰ روز و step-up پنج‌دقیقه‌ای را تثبیت کرده، اما MFA در هر ورود و محدودیت idle را باز گذاشته است. کاربر محصول سیاست پیشنهادی را تأیید کرده است. سامانه از role سفارشی و override پشتیبانی می‌کند، بنابراین تشخیص مدیر نباید به نام ثابت یک role متکی باشد.

## تصمیم

- «مدیر سامانه» برای این سیاست، کاربری است که IAM در لحظه‌ی ورود حداقل یک عضویت فعال با scope سراسری (`global`) برای او برمی‌گرداند. این تعریف با roleهای سفارشی و تغییرات role سازگار است. عضویت suspended/revoked یا bootstrap منقضی‌شده، admin login تلقی نمی‌شود.
- پس از OTP معتبر، Gateway برای این تشخیص به IAM زنده مراجعه می‌کند. اگر IAM در دسترس نباشد یا پاسخ قرارداد معتبر نداشته باشد، نشست صادر نمی‌شود؛ نبود پاسخ به‌عنوان نبود مدیر تفسیر نمی‌شود.
- ورود OTP مدیر، نشست موقت محدود به مسیرهای لازم MFA ایجاد می‌کند. نشست تا تأیید عامل موجود یا ثبت و تأیید عامل اولیه فقط اجازه‌ی وضعیت/enrollment/step-up MFA و خروج دارد؛ سایر APIها با `MFA_REQUIRED` رد می‌شوند. مهلت تکمیل MFA پنج دقیقه است. مدیر فاقد عامل باید همان‌جا TOTP را راه‌اندازی و تأیید کند؛ factor نهایی و recovery مطابق ADR-0006 است.
- احراز MFA در login فقط برای همان نشست است و step-up حساس همچنان حداکثر ۳۰۰ ثانیه اعتبار دارد. تغییر role یا disable/revoke عامل طبق نسخه‌ی policy/factor موجود و ارزیابی زنده‌ی IAM اعمال می‌شود.
- نشست مدیر پس از ۱۵ دقیقه عدم فعالیت منقضی و سمت سرور revoke می‌شود. زمان مطلق نشست همچنان ۳۰ روز و بدون تمدید لغزان است. cookie همان `HttpOnly`, `Secure` در production و `SameSite=Lax` می‌ماند؛ cookie به‌تنهایی idle timeout را کنترل نمی‌کند.
- نشست‌های غیرسراسری از عمر مطلق ۳۰ روزه‌ی فعلی پیروی می‌کنند. ارزیابی role و scope هر درخواست همچنان در سرور و از IAM انجام می‌شود.
- عملیات تغییر policy در کد و source فقط است؛ بازشدن gate writeهای production در ADR-0011، اجرای bootstrap، تغییر remote/GitHub و انتشار نیازمند تأیید جداگانه هستند.

## گزینه‌ها و trade-off

نگه‌داشتن MFA فقط برای عملیات حساس تجربه‌ی ورود ساده‌تری دارد، اما ورود مدیرِ فاقد step-up را برای مسیرهای کم‌حفاظت‌تر باقی می‌گذارد. MFA هر login و idle پانزده‌دقیقه‌ای ریسک دسترسی ناشی از نشست رهاشده را کم می‌کند، به قیمت وابستگی login مدیر به IAM و ورود مجدد بیشتر. تصمیم با fail-closed و مسیر enrollment محدود، این trade-off را می‌پذیرد.

## migration و rollback

- migration فقط ستون‌های نشست Gateway را به‌صورت additive اضافه می‌کند؛ نشست‌های قبلی در صورت نداشتن داده‌ی idle معتبر، برای scopeهای global پس از deploy دوباره احراز می‌شوند. هیچ role یا membership در migration تغییر نمی‌کند.
- rollback کد به نسخه‌ی قبل، ستون‌های additive را نگه می‌دارد؛ حذف ستون نیازمند migration مستقل بعد از پایان پنجره‌ی سازگاری است.
- برای کاهش ریسک rollout، قابلیت با تست واحد/integration و smoke مسیر OTP→MFA→API محافظت می‌شود. این ADR تأیید staging یا production نیست.
