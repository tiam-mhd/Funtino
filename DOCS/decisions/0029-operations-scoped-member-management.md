# ADR-0029: مدیریت اعضای scoped در پنل Operations

- تاریخ: 2026-10-18
- وضعیت: accepted؛ بر اساس درخواست صریح مالک محصول
- دامنه: Operations Web، API Gateway، Identity & Access و قراردادهای OpenAPI عمومی و داخلی

## مسئله و زمینه

صفحه‌ی اعضا در پنل مجموعه/شعبه باید از نظر تراکم، نوار عملیات و چرخه‌ی کار با فهرست نقش‌ها هم‌راستا باشد، اما رفتار roster فعلی فقط روی داده‌ی دریافت‌شده جست‌وجو می‌کند، فیلترهای آن سمت سرور نیستند و route جزئیات ۳۶۰ درجه ندارد. IAM مالک عضویت و نقش است؛ هویت نمایشی متعلق به API Gateway است.

## گزینه‌های بررسی‌شده

1. نگه‌داشتن جست‌وجو و فیلتر محلی روی صفحه‌ی دریافت‌شده؛ رد شد چون نتیجه‌ی کامل و قابل پیمایش نمی‌دهد.
2. کپی اطلاعات هویت به IAM برای جست‌وجوی نام؛ رد شد چون IAM مالک User نیست.
3. فیلتر و scope در IAM، افزودن هویت نمایشی پس از دریافت رکوردهای مجاز در Gateway، و ادامه‌ی cursor هنگام جست‌وجوی نام؛ انتخاب شد.
4. ساخت صفحه‌ی اعضا با رفتارهای مشابه ولی فرم‌ها و جزئیات غیرواقعی؛ رد شد چون هر اقدام باید به API و lifecycle مالک داده متصل باشد.

## تصمیم نهایی

- `/staff` فهرست اعضا و `/staff/members/{membershipId}` صفحه‌ی جزئیات همان عضو است. routeهای کاری در همان workspace و scope فعال اجرا می‌شوند. در جزئیات، عنوان بصری صفحه فقط عنوان header پوسته است.
- نوار فهرست از component مشترک Operations استفاده می‌کند. جست‌وجوی نام، نام خانوادگی، نام نقش و شماره‌ی پوشیده inline است؛ وضعیت، نقش و شعبه‌ی مقصد در صورت scope مجموعه داخل dialog فیلتر قرار می‌گیرند. ایجاد دعوت و ویرایش عضویت با modal انجام می‌شوند.
- در scope شعبه، فهرست دقیقاً عضویت‌های همان شعبه را برمی‌گرداند. در scope مجموعه، عضویت‌های مجموعه و شعبه‌های زیرمجموعه با نام همان محدوده گروه‌بندی می‌شوند. IAM scope، وضعیت، نقش، شعبه‌ی فیلتر و cursor را اعمال می‌کند؛ نمای `organizationTree` فقط با scope مجموعه معتبر است.
- Gateway پس از دریافت هر صفحه‌ی scope-مجاز، نام نمایشی را فقط برای `userId`های همان صفحه از User خودش می‌خواند و جست‌وجوی نام را روی نتیجه‌ی مجاز انجام می‌دهد. ادامه‌ی جست‌وجو با cursor رکوردهای بررسی‌شده انجام می‌شود؛ نتیجه‌ی کل یا ترتیب غیرقراردادی جعل نمی‌شود. IAM داده‌ی هویت را کپی یا جست‌وجو نمی‌کند.
- عنوان عضو از نام نمایشی، نام و نام خانوادگی ساخته می‌شود. اگر هیچ‌کدام موجود نباشند «عضو بدون نام نمایشی» نشان داده می‌شود و شماره فقط در قالب پوشیده، به‌عنوان اطلاعات ثانویه، قابل نمایش است. هیچ UUID یا شناسه‌ی فنی در متن فهرست، جزئیات، گروه یا پیام کاربر نمایش داده نمی‌شود. نام مجموعه/شعبه از scope option امن خوانده می‌شود و در نبود نام، عنوان «مجموعه/شعبه بدون نام نمایشی» به‌کار می‌رود.
- هر ردیف جزئیات، ویرایش نقش، وضعیت برگشت‌پذیر و لغو lifecycle را ارائه می‌کند. افزودن، دعوت مالکیت‌محور با شماره‌ی E.164 است و تا پذیرش صریح دعوت، عضویت را فعال نمی‌کند. تغییر نقش دعوت pending باید snapshot نقش دعوت را در همان تراکنش با عضویت هماهنگ کند.
- «حذف» داده‌ای برای عضویت تعریف نشده است. دکمه‌ی سطل زباله‌ی رابط، متن تأیید و نتیجه همواره lifecycle واقعی را دقیق توصیف می‌کنند: دعوت pending لغو می‌شود و عضویت فعال/معلق به‌طور دائمی revoke می‌شود. دلیل، MFA تازه، مجوز، scope، idempotency، audit و invariant آخرین مدیر طبق ADR-0008 و ADR-0025 اعمال می‌شوند. تعلیق/فعال‌سازی دوباره برگشت‌پذیر و جدا از لغو دائمی است.
- جزئیات ۳۶۰ درجه وضعیت، محدوده، نقش، مجوزهای نقش با label انسانی، زمان‌های lifecycle، شماره‌ی پوشیده، overrideهای قابل مشاهده و اعضای دارای همان نقش در محدوده‌ی قابل‌مشاهده را نشان می‌دهد. overrideها به `access.role.read` و فهرست اعضای هم‌نقش به `staff.read` وابسته‌اند؛ نبود هر مجوز فقط همان بخش را محدود می‌کند.
- فهرست اعضا از header پوسته عنوان می‌گیرد و heading تکراری ندارد. نوار عملیات، modalها و route جزئیات RTL، واکنش‌گرا، قابل‌استفاده با صفحه‌کلید و دارای loading/empty/error/no-access state هستند.

## پیامدها و trade-offها

- قرارداد فهرست IAM، Gateway و frontend باید وضعیت، نمای scope، شعبه، شناسه‌ی عضویت برای lookup جزئیات، جست‌وجوی Gateway و metadata lifecycle لازم را پوشش دهد.
- جست‌وجوی نام با اسکن cursor محدود به چند صفحه‌ی IAM در هر درخواست انجام می‌شود؛ اگر نتیجه‌ی بیشتری در دسترس باشد، رابط امکان ادامه‌ی جست‌وجو را نشان می‌دهد. این روش بدون ایجاد read model هویتی مستقل، نتیجه‌ی کامل را قابل پیمایش می‌کند.
- جست‌وجوی inline و modal ساخت/ویرایش استثنای محدود قواعد عمومی فهرست است؛ scope، permission، validation و lifecycle همچنان در سرور enforce می‌شوند.
- migration دیتابیس لازم نیست؛ داده‌ی lifecycle در schema موجود IAM ثبت شده است.

## بسترها و سرویس‌های اثرپذیرفته

- `operations-web`: فهرست، modalهای دعوت/ویرایش/تأیید، route جزئیات و گروه‌بندی نمایشی.
- `api-gateway`: قرارداد عمومی فهرست/جزئیات، افزودن نام نمایشی و جست‌وجوی صفحه‌دار.
- `identity-access`: scope/status/role/branch filters و metadata lifecycle در پاسخ roster.
- قراردادهای `contracts/openapi/gateway.yaml` و `contracts/openapi/identity-access.yaml`.
- runtime bundleهای frontend و backend به دلیل تغییر هم‌زمان UI و قرارداد/API اثر می‌پذیرند.

## برنامه‌ی migration یا rollback

- تغییری در دیتابیس یا migration نیست. در rollback رابط، APIهای افزایشی و پارامترهای اختیاری برای مصرف‌کنندگان قدیمی سازگار می‌مانند.
- source monorepo مرجع است؛ controlled snapshot هر دو runtime طبق ماتریس اثر و workflow canonical Runflare انجام می‌شود.
