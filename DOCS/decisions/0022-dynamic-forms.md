# ADR-0022: فرم‌ساز چندمجموعه‌ای و مالکیت پاسخ‌ها

- تاریخ: 2026-10-11
- وضعیت: accepted
- تصمیم‌گیر: مالک محصول
- دامنه: Forms، API Gateway، Identity & Access، سه وب‌اپ، PostgreSQL و runtime backend

## زمینه

فرم‌های عمومی و عملیاتی باید در سه بستر مشتری، عملیات و سیستم قابل مدیریت/مصرف باشند. فرم و پاسخ مالک دامنه‌ای جدا از حساب مشتری، شعبه، کیف پول و گزارش‌های موجود دارند. پیش‌نمایش و فرم منتشرشده باید یک schema و renderer مشترک داشته باشند. پاسخ‌ها ممکن است دادهٔ شناسایی‌کننده داشته باشند.

## تصمیم

- تعریف فرم در نسخهٔ ۲، صفحه‌های مستقل شروع، پرسش و پایان، شرط نمایش صفحه، چیدمان فیلد و ظاهر کلی/صفحه‌ای کارت را پشتیبانی می‌کند. schema مشترک نسخهٔ ۱ را می‌پذیرد و آن را به مدل نسخهٔ ۲ نرمال می‌کند؛ پیش‌نویس‌ها و snapshotهای تازه با نسخهٔ ۲ ذخیره می‌شوند. snapshot منتشرشده همچنان تغییرناپذیر است.
- سرویس جدید `services/forms` مالک فرم، نسخهٔ تغییرناپذیر منتشرشده، پاسخ، template، یادداشت/برچسب عملیاتی، audit و Outbox است. داده‌ها در schema اختصاصی `forms` قرار می‌گیرند؛ هیچ سرویس دیگری مستقیماً جدول‌های آن را نمی‌خواند یا می‌نویسد.
- PostgreSQL منبع حقیقت فرم و پاسخ است. هر پاسخ به `organizationId`، `branchId`، `formId` و `formVersionId` متصل و با idempotency key یکتا ثبت می‌شود. snapshot نسخه و پاسخ‌های شناسه‌دار با field ID پایدار، نمایش تاریخی و گزارش را ممکن می‌کنند.
- API Gateway تنها ingress مرورگر است. Gateway پیش از هر عملیات مدیریتی مجوز IAM را با resource و scope سازمان/شعبهٔ معتبر ارزیابی می‌کند و شعبه را از Owner سازمان/شعبه اعتبار می‌سنجد. سرویس Forms درخواست داخلی را فقط از Gateway با service token می‌پذیرد؛ caller scope داخل payload به‌تنهایی مدرک دسترسی نیست.
- دسترسی به پاسخ فردی، دیدن اطلاعات شناسایی‌کننده، ویرایش وضعیت، انتشار، export و مدیریت template مجوزهای جدا دارند. دسترسی به پاسخ دارای PII در UI سیستم وجود ندارد؛ مسیرهای حساس باید مجوز `forms.responses.pii.read` و ثبت audit بدون محتوای پاسخ داشته باشند. مدیر سیستم فقط فراداده و آمار تجمیعی را از بستر سیستم می‌بیند.
- وضعیت پاسخ فقط در این مسیرها تغییر می‌کند: `new → in_review|closed|spam`، `in_review → followed_up|closed|spam`، `followed_up → in_review|closed|spam`، `closed → in_review` و `spam → in_review|closed`. هر گذار دیگر با conflict رد می‌شود و دلیل تغییر audit می‌شود.
- نقش‌های `organization_manager` و `branch_manager` فقط مجوزهای مدیریتی فرم/پاسخ غیرحساس را به‌عنوان پیش‌فرض دریافت می‌کنند؛ مجوز PII به templateهای پیش‌فرض اضافه نمی‌شود.
- نسخهٔ منتشرشده immutable است. هر تغییر طراحی در draft انجام می‌شود و انتشار نسخهٔ تازه، پاسخ‌های قبلی را دست‌کاری نمی‌کند. رویدادهای نسخه‌دار از Outbox منتشر می‌شوند؛ consumerها باید Inbox و idempotency داشته باشند و payload هیچ پاسخ یا PII را حمل نمی‌کند.
- اصلاح پاسخ بعد از ثبت، فقط با مجوز جداگانه انجام می‌شود. مقدار فعلی در تراکنش به‌روز می‌شود و برای هر field تغییرکرده، مقدار قبل/بعد، actor، دلیل، زمان و نسخه در دفتر append-only نگه داشته می‌شود؛ رویداد اصلاح فقط شناسه‌ها و تعداد فیلدها را دارد. اصلاح فیلد حساس به `forms.responses.pii.read` و MFA step-up نیاز دارد.
- پاسخ مهمان بدون ساخت حساب مجاز است اگر تنظیم انتشار اجازه دهد. اتصال پاسخ به حساب مشتری اختیاری، پس از احراز معتبر و رضایت صریح است. هویت یا scope شعبه از دادهٔ دست‌کاری‌پذیر فرم استخراج نمی‌شود.
- تا تصویب سیاست retention پاسخ‌ها نگهداری می‌شوند و پاک‌سازی/ناشناس‌سازی خودکار اجرا نمی‌شود. محتوای پاسخ و PII در log، URL، رویداد یا خطای قابل مشاهده ثبت نمی‌شود. حذف دستی نیز باید مجوز و audit داشته باشد.
- فایل عمومی/امضای دیجیتال در این مرحله فعال نمی‌شود؛ مخزن زیرساخت object storage عمومی و provider مصوب ندارد. فیلدهای فایل، تصویر و امضا تا انتخاب provider، سیاست اندازه/نوع، مجوز دانلود و retention در کتابخانهٔ قابل استفاده نمایش داده نمی‌شوند. این تصمیم به upload آواتار محدود موجود تسری ندارد.
- پکیج `packages/forms-schema` قرارداد نسخه‌دار schema، validation شرطی و پاک‌سازی پاسخ را نگه می‌دارد. `packages/forms-renderer` renderer مشترک React برای پیش‌نمایش واقعی builder و runtime مشتری است؛ منطق دامنه در این packageها قرار نمی‌گیرد.
- مجوز هر بستر از API Gateway صادر می‌شود. پنل سیستم مدیریت global template/تنظیمات و فراداده را انجام می‌دهد؛ پنل عملیات مدیریت scopeدار مجموعه/شعبه، پاسخ‌ها و export کنترل‌شده را انجام می‌دهد؛ customer web فرم عمومی/مجاز را render و submit می‌کند.
- سرویس جدید روی port `4090` در backend bundle اجرا می‌شود. migration آن manual و نسخه‌دار و جدا از startup است؛ Forms جزو پنج Worker استثنای ADR-0015 نیست.

## قراردادها و آثار اجرایی

- OpenAPI عمومی Forms در `contracts/openapi/forms-gateway.yaml` و قرارداد داخلی در `contracts/openapi/forms-internal.yaml` تعریف می‌شوند؛ schema مشترک فرم در `contracts/schemas/forms/form-definition.v1.schema.json` است.
- رویدادهای Forms در `packages/event-contracts` نسخه‌دار و بدون پاسخ/PII تعریف می‌شوند.
- runtime backend شامل `@funtino/forms`، manifest، environment allow-list، build check و port `4090` است. Forms و Gateway فقط متغیرهای runtime مجاز خود را می‌گیرند.
- shared schema/renderer و API contracts تغییر frontend و backend bundle را اثرپذیر می‌کنند؛ هر دو bundle باید در یک انتشار کنترل‌شده همگام شوند.
- مسیرهای احتمالی UI: `operations-web/.../forms`، `system-web/.../forms` و `customer-web/.../forms/[slug]`.

## محدودیت‌ها و پیامدها

- نرخ ارسال مهمان باید در Gateway با زیرساخت rate limit موجود محافظت شود؛ اگر rate limit پایدار/سراسری موجود نباشد، rollout عمومی نیازمند gate عملیاتی است.
- ذخیره‌سازی upload، امضا و مدیای اختصاصی فرم تا ADR/provider جداگانه غیرفعال می‌ماند.
- پاسخ‌ها تا تصویب سیاست retention پاک‌سازی خودکار نمی‌شوند؛ مالک محصول باید سیاست و زمان‌بندی را پیش از فعال‌کردن پاک‌سازی ثبت کند.
- گزارش تجمیعی نباید امکان بازشناسایی پاسخ فردی را از طریق ابعاد کوچک/فیلترهای دقیق فراهم کند.
