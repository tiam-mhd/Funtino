# راهنمای معماری و منطق قابلیت NFC موجودی کارت

## دامنهٔ راهنما

این سند مبنای پرامپت اجرایی برای مخزن وب Funtino است و به آخرین منبع بررسی‌شده در **۲۲ نوامبر ۲۰۲۶** تکیه دارد:

- Web `tiam-mhd/Funtino`: `ff0c364da458b5d1c0eac0bbcba9529989feab7f` (`main`).
- Windows `tiam-mhd/FuntinoCashWindows`: `b6a31dc5e354457faebf61e024729f6f87b24255` (`main`).

هنگام اجرای پرامپت، هر دو HEAD را دوباره بررسی کن؛ اگر کد جلو رفته، نسخهٔ فعلی منبع حقیقت است.

## Windows اکنون دقیقاً چه می‌کند؟

منبع: [CardReaderService.cs در revision بررسی‌شده](https://github.com/tiam-mhd/FuntinoCashWindows/blob/b6a31dc5e354457faebf61e024729f6f87b24255/FuntinoControlCenter/Services/CardReaderService.cs)

مسیر `ReadBalance()` این مراحل را انجام می‌دهد:

1. مجوز محلی `cards.balance.view` را بررسی می‌کند.
2. یک عملیات خواندن در دیتابیس محلی ثبت می‌کند و `ReaderSession` را با پورت سریال تنظیم‌شده و کلید کارت باز می‌کند.
3. فرمان درخواست کارت را می‌فرستد و پاسخ کارت‌خوان را تا timeout بررسی می‌کند.
4. anti-collision را می‌فرستد و **UID چهار‌بایتی** می‌گیرد.
5. فریم انتخاب کارت را با UID می‌سازد و XOR checksum آن را محاسبه می‌کند.
6. کلید **شش‌بایتی** را روی reader بار می‌کند.
7. با فرمان authenticate روی **بلوک ۸** احراز هویت می‌کند.
8. یک بلوک ۱۶‌بایتی را می‌خواند. `ToToman` چهار بایت اول را با `BitConverter.ToUInt32(data, 0)` می‌گیرد و در `100` ضرب می‌کند.
9. پایان عملیات را ثبت می‌کند و کارت را halt می‌کند.

روی Windows مورد بررسی، `BitConverter.ToUInt32` عملاً مقدار little-endian می‌سازد؛ پیاده‌سازی مشترک یا تست fixture باید صریحاً little-endian باشد و به endianness دستگاه اجرا وابسته نشود. مقدار خام بلوک به تومان است. در تبدیل به ریال، هر تومان ۱۰ ریال است؛ تبدیل واحد را با نوع عددی صحیح/ایمن انجام بده.

`ReadBalance()` در نتیجهٔ داخلی خود `CardInformation` هم برمی‌گرداند؛ این مدل فیلدهایی مثل `Uid`، `UidBytes`، `CardType`، `ExpirationDate` و `DiscountPercent` دارد. نمایش Web باید این فیلدها را کنار بگذارد و فقط مبلغ مجاز را بگیرد.

تابع Edge در [EdgeIntegrationRepository.cs](https://github.com/tiam-mhd/FuntinoCashWindows/blob/b6a31dc5e354457faebf61e024729f6f87b24255/FuntinoControlCenter/Database/EdgeIntegrationRepository.cs) فقط UID دقیقاً ۴ بایتی را می‌پذیرد، آن را به hex بزرگ بدون جداکننده تبدیل می‌کند و SHA-256 از متن UTF-8 می‌گیرد. بردار کنترل `01020304` به `34b8d380d481b933d5238d945a16ee6c0be176960926735bce473b829e4bd517` می‌رسد. این hash برای نگاشت Edge است؛ مالکیت، رمزنگاری کارت یا مجوز دسترسی نیست.

## وضعیت وب موجود

### اپلیکیشن مشتری

- صفحهٔ کارت‌ها در مسیر `apps/customer-web/src/app/[locale]/cards/page.tsx` با `CustomerShell` رندر می‌شود.
- رابط فعلی در `apps/customer-web/src/components/customer-cards.tsx` از `@funtino/design-system`، `Surface` و `Badge` استفاده می‌کند و تاریخچه، assignment و freshness را نمایش می‌دهد.
- Gateway در `apps/api-gateway/src/interfaces/http/customer.controller.ts` مسیر احراز‌شدهٔ `GET /api/v1/customer/cards` دارد.
- `CustomerService.listCards()` در `apps/api-gateway/src/application/customer/customer.service.ts` householdهای کاربر را می‌گیرد، assignmentهای Wallet را می‌خواند، سپس `getCardLedgerSummary(householdId, cardId)` را فراخوانی می‌کند. پاسخ فعلی شامل شناسه و masked ID و status و `balanceRial` و freshness است؛ نباید این DTO کامل را برای رابط اسکن دوباره استفاده یا بی‌دلیل به endpoint عمومی جدید منتقل کرد.
- `balanceRial` از projection مرکزی Wallet است. این مبلغ لزوماً همان چیزی نیست که اکنون از بلوک فیزیکی کارت خوانده می‌شود؛ freshness و snapshot تأییدشده تعیین می‌کنند اصلاً نمایش عدد مجاز هست یا نه.

### Wallet و Edge

- Wallet یک route داخلی `GET /internal/v1/households/:householdId/cards/:cardId/summary` با `WalletServiceTokenGuard` دارد.
- `GET /internal/v1/organizations/:organizationId/branches/:branchId/edge-card-mappings` با guard مخصوص device integration، `cardUidHash`، cardId و household/member mapping را برای دستگاه معتبر برمی‌گرداند. این route برای Windows/Edge است و public/customer endpoint نیست.
- در revision بررسی‌شده، route عمومی Web برای resolve کردن UID اسکن‌شده به balance وجود ندارد. اگر لازم شد، Gateway باید احراز هویت/مالکیت را انجام دهد و با Wallet از طریق client داخلی صحبت کند؛ browser نباید مستقیم Wallet یا DB را صدا بزند.

### پنل Operations

- پنل کارت از `apps/operations-web/src/features/cashier/CardInventoryManagement.tsx` و `HouseholdCardAssignments.tsx` تشکیل شده و branch/org scope موجود را مصرف می‌کند.
- `OperationsCardsController` در `apps/api-gateway/src/interfaces/http/operations-cards.controller.ts` برای `GET /api/v1/operations/organizations/:organizationId/branches/:branchId/cards` `card.inventory.read` را بررسی می‌کند و `assertActiveScope` را اجرا می‌کند.
- اینها الگوی مناسبی برای scope هستند؛ مجوز دیدن موجودی ممکن است از دید کسب‌وکار حساس‌تر از مجوز فهرست کارت باشد. اگر permission مستقل `card.balance.read` لازم است، آن را در مسیر policy/identity کامل اضافه کن و نقش‌های موجود را بی‌صدا گسترش نده.

## حد فنی مرورگر

مستند رسمی [Chrome Web NFC](https://developer.chrome.com/docs/capabilities/nfc) می‌گوید Web NFC برای NDEF است و low-level I/O مانند ISO-DEP و NFC-A/B/F را پشتیبانی نمی‌کند. بنابراین صفحهٔ وب نمی‌تواند همان authenticate روی بلوک ۸ با key شش‌بایتی را مستقیماً از JavaScript انجام دهد. Web NFC فقط وقتی قابل‌استفاده است که مرورگر و کارت واقعی دادهٔ قابل‌خواندن موردنیاز lookup را بدهند؛ این را روی کارت و گوشی هدف آزمایش کن.

اگر خواندن مستقیم MIFARE Classic مدنظر باشد، مستند رسمی Android نیز می‌گوید API `MifareClassic` اختیاری است و ممکن است روی بعضی دستگاه‌ها پیاده نشده باشد؛ خود API نیز احراز هویت کلید ۶ بایتی برای sector را انجام می‌دهد. این به معنی پشتیبانی همهٔ گوشی‌های Android نیست. [Android MifareClassic](https://developer.android.com/reference/android/nfc/tech/MifareClassic)

پس سه مفهوم را جدا نگه دار:

| مسیر | چه چیزی واقعاً خوانده می‌شود؟ | منبع موجودی | ادعای مجاز در UI |
|---|---|---|---|
| Web NFC در مرورگر | فقط داده‌ای که API و کارت واقعی در اختیار مرورگر می‌گذارند؛ معمولاً NDEF، نه بلوک محافظت‌شده | Wallet مرکزی پس از resolve امن و freshness معتبر | «موجودی قابل‌تأیید»؛ نه خواندن مستقیم حافظهٔ کارت |
| پل بومی/reader مورداعتماد | بلوک فیزیکی ۸ مطابق منطق Windows، فقط اگر پل/کلید/سخت‌افزار واقعاً پشتیبانی شود | مقدار parseشدهٔ خود چیپ | موجودی خوانده‌شده از کارت |
| Wallet بدون اسکن قابل‌اعتبار | هیچ کارت فیزیکی در این درخواست شناسایی نشده | snapshot قبلی | نباید به‌عنوان نتیجهٔ اسکن یا موجودی فعلی نمایش داده شود |

اسکن UID و نمایش balance از Wallet می‌تواند تجربهٔ NFC ایجاد کند، اما معادل خواندن مستقیم بلوک ۸ نیست. اگر این تفاوت برای محصول پذیرفتنی نیست، پل بومی امن و آزمایش سخت‌افزاری جزء وابستگی واقعی کار است.

## قواعد امنیتی

- UID چهار‌بایتی فضای جست‌وجوی کوچکی دارد؛ hash SHA-256 آن هم قابل brute-force است. hash را token محرمانه تصور نکن.
- پاسخ lookup را به customer session و فهرست householdهای همان کاربر محدود کن. برای عملیات، scope سازمان/شعبه و permission را سمت Gateway کنترل کن.
- پاسخ کارت ناموجود و کارت متعلق به شخص دیگر باید از نظر متن/جزئیات قابل‌تفکیک نباشد؛ نرخ درخواست محدود شود.
- raw UID، hash، cardId، key، block bytes و موجودی نباید در URL، log، analytics یا cache پایدار ثبت شوند. در response فقط مبلغ و وضعیت لازم برای UI بماند.
- برای اسکن فقط API خواندن به‌کار ببر. NFC writer، `WriteBlock`، `Transfer`، top-up یا ledger mutation در flow اسکن قابل‌فراخوانی نباشد.
- در هیچ شرایطی key کارت را در bundle وب نگذار. اگر پل بومی به key نیاز دارد، امنیت کلید، origin allowlist، امضای برنامه، چرخهٔ تعویض کلید و ممیزی باید در سند جداگانه تأیید شود.

## تصمیم پیشنهادی

برای Funtino Web، UI و API را بر اساس provider adapter بساز تا منبع اسکن قابل‌تعویض و تست‌پذیر باشد. مسیر Web NFC در صورت کار روی کارت واقعی فقط UID/hash را برای lookup می‌دهد و API مبلغ Wallet را برمی‌گرداند، به شرط assignment مالک و freshness. مسیر خوانش مستقیم بلوک ۸ فقط از پل مورداعتماد انجام می‌شود و در صورت نبود پل/کلید امن/هاردور باید به‌عنوان وابستگی باز ثبت شود. هیچ‌گاه این دو منبع را خودکار با هم جمع، جایگزین یا reconciliation نکن.
