# قرارداد پیشنهادی پل خوانش کارت برای Web

## چرا این قرارداد لازم است؟

PWA داخل مرورگر اجازهٔ بازسازی امن و مستقیم مسیر Windows برای احراز هویت با key شش‌بایتی و خواندن بلوک خام ۸ را ندارد. این سند مرز بین UI وب و یک provider مورداعتماد را تعریف می‌کند تا UI هرگز key، UID خام یا بایت‌های حافظه را نبیند.

این قرارداد به‌تنهایی پل عملیاتی نمی‌سازد. پیش از ادعای پشتیبانی، باید مشخص شود provider واقعی کدام است: Web NFC برای lookup روی Wallet، برنامهٔ بومی Android، یا agent محلی مورداعتماد برای reader شعبه.

## دو عملیات جدا و غیرقابل‌جایگزینی

### A. اسکن مرورگر برای lookup در Wallet

این مسیر فقط وقتی مجاز است که `NDEFReader` و کارت/گوشی واقعی شناسهٔ قابل‌تطبیق بدهند. منبع مبلغ Wallet مرکزی است، نه حافظهٔ کارت.

1. با اقدام روشن کاربر scan را آغاز کن.
2. capability و permission مرورگر را بررسی کن؛ هیچ write روی tag اجرا نکن.
3. اگر کارت واقعی شناسهٔ سریال قابل‌دسترسی دارد، آن را در حافظهٔ کوتاه‌عمر canonicalize کن. روش canonicalization با ۴‌بایتی Windows و golden vector تطبیق داده شود؛ رشتهٔ hex به‌صورت uppercase و بدون separator ساخته شود.
4. از Web Crypto برای SHA-256 دقیقاً مطابق mapping فعلی Windows استفاده کن، یا اگر قرارداد Gateway امن‌ترِ سازگار تعریف کرد از همان پیروی کن. هیچ secret سمت frontend اضافه نکن.
5. فقط مقدار لازم برای lookup را با HTTPS و session فعلی به Gateway بفرست؛ از query string استفاده نکن.
6. با پایان درخواست، raw UID و hash را از state و log پاک کن.
7. Gateway باید مالکیت و وضعیت کارت را کنترل کند و فقط اگر Wallet freshness معتبر است مبلغ را بازگرداند.

نمونهٔ معنایی درخواست؛ نام route و فیلد نهایی باید با API conventions مخزن یکی باشد:

```http
POST /api/v1/customer/cards/nfc-balance
Content-Type: application/json
```

```json
{ "cardUidHash": "hex-encoded-32-byte-digest" }
```

نمونهٔ پاسخ موفق حداقلی:

```json
{ "status": "available", "balanceRial": 1250000 }
```

نمونهٔ پاسخ غیرقابل‌نمایش:

```json
{ "status": "unavailable" }
```

Gateway نباید برای موفقیت عمومی `cardId`، `householdId`، `memberId`، `cardUidHash`، masked ID یا دادهٔ reconciliation را بازگرداند. پاسخ شخصی `Cache-Control: no-store` داشته باشد. hash، چون مشتق UID چهار‌بایتی است، محرمانه یا مجوز حساب محسوب نمی‌شود؛ مالکیت احراز‌شده، محدودسازی نرخ و پاسخ یکنواخت اجباری‌اند.

### B. خواندن مستقیم بلوک فیزیکی کارت

این مسیر فقط از برنامهٔ بومی/agent مورداعتماد می‌گذرد. کلید از JavaScript، صفحهٔ وب، query string یا body عمومی ردوبدل نمی‌شود. provider فقط نتیجهٔ خواندن را تحویل می‌دهد؛ UI نباید protocol frame، UID یا block bytes دریافت کند.

نمونهٔ قرارداد معنایی داخل لایهٔ adapter؛ نه الزام به global جاوااسکریپتی خاص:

```ts
type PhysicalCardBalanceResult =
  | { status: 'success'; balanceToman: string; readAtUtc: string }
  | { status: 'no_card' | 'unsupported' | 'key_rejected' | 'reader_unavailable' | 'card_lost' | 'error' };

interface PhysicalCardBalanceProvider {
  readBalance(): Promise<PhysicalCardBalanceResult>;
  cancel?(): Promise<void>;
}
```

قواعد پل:

- `readBalance` فقط می‌خواند؛ عملیات write/transfer/increment/decrement در قرارداد تعریف نشود.
- `balanceToman` مبلغ صحیح non-negative و محدود به بازهٔ مجاز Windows باشد؛ string عددی استفاده شود تا overflow/precision در JSON/JavaScript کنترل شود.
- پل مقدار خام بلوک، key، UID، شناسهٔ کارت و اطلاعات فنی reader را به UI ندهد.
- فقط origin دقیق و HTTPS فانتینو و برنامهٔ امضاشده/شناخته‌شده مجاز باشند. پروتکل پیام نسخه‌دار، request id، timeout، cancellation و کنترل replay داشته باشد.
- مقدار نهایی صرفاً برای نمایش باشد و هرگز به عنوان فرمان مالی یا ورودی ledger پذیرفته نشود.
- کلید مشترک در اپ موبایل/agent کپی نشود مگر امنیت آن جداگانه با key diversification/مدیریت کلید/rotation و مدل تهدید تأیید شده باشد. اگر راهکار فعلی Windows از کلید مشترک استفاده می‌کند، انتقال همان کلید به یک کلاینت عمومی پذیرفته نیست.
- پشتیبانی Android به مدل گوشی/چیپ وابسته است. روی دستگاه‌های هدف و کارت واقعی بررسی شود؛ وجود Android NFC به‌تنهایی تضمین پشتیبانی MIFARE Classic نیست.
- برای پنل شعبه روی PC، اگر reader سریال فعلی نیاز به bridge دارد، agent محلی باید install/pair شده و به origin فانتینو محدود باشد. Web Serial/WebUSB با key در bundle جایگزین امن نیست.

## قرارداد API داخلی

### Customer Gateway → Wallet

- Gateway session مشتری را بررسی کند.
- Gateway با `CustomerHouseholdClient` householdهای مجاز را تعیین کند.
- Wallet فقط assignment فعال/تأییدشده را با `cardUidHash` و مجموعهٔ household مجاز resolve کند.
- Wallet summary را از منبع canonical بخواند و freshness/pending را ارزیابی کند.
- Gateway پاسخ عمومی را به `{status, balanceRial?}` کوچک کند.
- درخواست lookup ناموجود، مسدود، unlinked یا متعلق به household دیگر نباید اطلاعات قابل‌استفاده دربارهٔ وجود کارت بدهد.

### Operations Gateway → Wallet

- Gateway session و capability کاربر را با scope نوع branch بررسی کند.
- سازمان و شعبه باید active و متعلق به هم باشند.
- Wallet lookup فقط در organization/branch همان درخواست انجام شود.
- response عمومی فقط وضعیت و مبلغ داشته باشد؛ audit حداقلی جداگانه ثبت شود.

در هر دو مسیر، مرورگر حق دسترسی به `WalletServiceToken`، routeهای `/internal/v1/...` یا دیتابیس را ندارد. از query string برای UID/hash استفاده نشود و پاسخ `no-store` باشد.

## قرارداد provider داخل Web

در Web یک interface کوچک با implementationهای جدا بساز؛ نام‌ها با conventions فعلی پروژه تطبیق داده شوند:

```ts
type CardScanResult =
  | { status: 'identifier_available'; cardUidHash: string }
  | { status: 'unsupported' | 'permission_denied' | 'no_card' | 'read_error' };

interface CardScanProvider {
  scan(): Promise<CardScanResult>;
  cancel?(): Promise<void>;
}
```

Web NFC provider فقط feature-detect/permission/scan را مدیریت کند. Business authorization و balance query در Gateway باشد. Physical native provider — اگر واقعاً ساخته/موجود شد — باید interface جدا داشته باشد تا ledger snapshot به‌اشتباه نتیجهٔ raw read قلمداد نشود.

## زمان‌بندی و خطا

- Scan فقط با اقدام کاربر شروع شود؛ در صورت خروج صفحه یا تغییر scope cancel شود.
- در حالت stale/pending/unknown، مبلغ را از response حذف کن یا UI را وادار به پنهان‌کردنش کن.
- خطاهای `not found`، `belongs to another user` و `not assigned in branch` پاسخ قابل‌تمایز به کاربر ندهند.
- گزارش‌های backend باید UID، hash، کلید، block bytes و مبلغ را redacted کنند.
- `requestId` صرفاً برای correlation غیرحساس است و نباید مشتق شناسهٔ کارت باشد.
