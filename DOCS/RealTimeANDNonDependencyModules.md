درست است؛ این شرط باید از ابتدا در معماری لحاظ شود. با آن، پیشنهاد قبلی را این‌طور به‌روزرسانی می‌کنم: فانتینو باید **رویدادمحور و متشکل از سرویس‌های مستقل** باشد، نه یک بک‌اند واحد با ماژول‌هایی که مستقیم همدیگر را صدا می‌زنند.

> **وضعیت این فایل:** این سند تحلیل مرجع و ورودی تصمیم معماری است، نه دستور اجرایی مستقل. انتخاب NATS JetStream در نسخه‌ی اولیه‌ی این تحلیل، برای استقرار نهایی Runflare superseded شده است. طبق [TechAnalysis.md](TechAnalysis.md)، [AGENTS.md](../AGENTS.md) و [ADR-0002](decisions/0002-runflare-deployment-repositories.md)، پیام‌رسان تولیدی پیش‌فرض RabbitMQ مدیریت‌شده‌ی Runflare است. اصول استقلال سرویس، Outbox/Inbox، idempotency و Realtime این سند همچنان معتبرند.

یک نکته‌ی مهم: استقلال کاملِ بدون هیچ قرارداد یا زیرساخت مشترک ممکن نیست. سرویس‌ها باید درباره‌ی قالب رویدادها توافق داشته باشند و از زیرساخت‌هایی مثل هویت و پیام‌رسان استفاده کنند. هدف این است که هر سرویس **کد، داده و استقرار خودش را داشته باشد** و برای انجام کارهای عادی به فراخوانی مستقیم سرویس دیگری وابسته نشود.

## معماری به‌روزشده

| بخش                        | فناوری پیشنهادی                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------- |
| وب‌اپ مشتری                | Next.js و TypeScript، به‌صورت PWA                                                      |
| پنل صندوق و مدیریت         | Next.js و TypeScript                                                                   |
| سرویس‌های کسب‌وکار         | NestJS و TypeScript، هرکدام مستقل و قابل استقرار جداگانه                               |
| دیتابیس                    | PostgreSQL؛ مالکیت داده جدا برای هر سرویس                                              |
| پیام‌رسان رویدادها         | NATS JetStream                                                                         |
| به‌روزرسانی زنده‌ی رابط‌ها | NestJS WebSocket Gateway با Socket.IO                                                  |
| Cache                      | Redis؛ برای cache و rate limit، نه ثبت تراکنش                                          |
| APIهای هم‌زمان             | REST و OpenAPI                                                                         |
| قرارداد رویدادها           | JSON Schema و AsyncAPI، با نسخه‌بندی                                                   |
| اجرای محلی                 | Docker Compose                                                                         |
| استقرار تولید              | کانتینرهای مستقل؛ Kubernetes یا سرویس مدیریت‌شده‌ی کانتینر با توجه به توان عملیاتی تیم |

NestJS هم NATS را برای ارتباط رویدادمحور پشتیبانی می‌کند و هم WebSocket Gateway دارد؛ Gateway می‌تواند با Socket.IO یا `ws` کار کند. NATS JetStream هم پیام‌های پایدار و مصرف‌کننده‌های قابل‌بازیابی فراهم می‌کند.

## مرز سرویس‌ها

ماژول‌ها را بر اساس مسئولیت کسب‌وکار جدا کن، نه بر اساس صفحه‌های اپلیکیشن:

1. **Identity & Access:** حساب کاربری، ورود، نقش‌ها و دسترسی به شعب.
2. **Organization & Branch:** فانتینو، شعب، ساعت کاری و تنظیمات عملیاتی.
3. **Customer & Household:** پروفایل مشتری، خانواده، سرپرست و اعضای وابسته.
4. **Wallet:** کارت‌های متصل، اعتبار، هدیه، امتیاز و دفتر تراکنش.
5. **Payment & Orders:** سفارش شارژ، پرداخت، تأیید و برگشت.
6. **Device Integration:** اتصال به سامانه‌ی کارت، کاهنده‌ها و دستگاه‌ها.
7. **Loyalty & CRM:** مأموریت، کمپین، امتیاز، کوپن و بخش‌بندی مشتری.
8. **Notifications:** پیامک و اعلان.
9. **Realtime Gateway:** دریافت رویدادها و رساندن به‌روزرسانی زنده به وب‌اپ‌ها.
10. **Analytics/Read Model:** گزارش‌ها و مدل‌های خواندنی برای صفحات تجمیعی.

هر سرویس دیتابیس یا schema و migration خودش را مالک باشد. سرویس‌ها مستقیماً جدول‌های یکدیگر را نخوانند یا تغییر ندهند. در شروع می‌توان دیتابیس‌های منطقی جدا را روی یک کلاستر PostgreSQL اجرا کرد و بعد، در صورت نیاز، آن‌ها را به کلاسترهای جدا انتقال داد.

## جریان رویدادها

مسیر معمول یک تغییر چنین است:

```text
درخواست مشتری یا دستگاه
       ↓
سرویس مالک آن عملیات
       ↓
ثبت در دیتابیس خودش و ساخت رویداد
       ↓
NATS JetStream
       ↓
سرویس‌های علاقه‌مند به آن رویداد
       ↓
Read Model و WebSocket Gateway
       ↓
به‌روزرسانی صفحه‌ی مشتری یا کارکنان
```

برای نمونه، با ثبت پرداخت، سرویس پرداخت رویداد `PaymentConfirmed` را منتشر می‌کند. سرویس کیف پول آن را می‌خواند، اعتبار را در دیتابیس خودش ثبت می‌کند و رویداد `WalletCredited` می‌فرستد. سرویس وفاداری و درگاه زنده هم می‌توانند جداگانه به آن واکنش نشان دهند. اختلال در CRM نباید جلوی ثبت پرداخت را بگیرد.

رویدادها را از ابتدا با این اطلاعات استاندارد کن: `eventId`، نوع و نسخه‌ی رویداد، زمان وقوع، `organizationId`، `branchId`، شناسه‌ی منبع، و `correlationId`. مصرف‌کننده‌ها باید تکراری‌بودن پیام را تشخیص دهند؛ پیام‌های JetStream ممکن است دوباره تحویل شوند و پردازش باید idempotent باشد.

برای اینکه تغییر دیتابیس و انتشار رویداد از هم جا نمانند، هر سرویس جدول **Outbox** خودش را داشته باشد. رکورد کسب‌وکار و رویداد outbox در یک تراکنش PostgreSQL ذخیره می‌شوند؛ بعد یک publisher رویداد را به NATS می‌فرستد. مستندات Debezium این الگو را برای تبادل قابل‌اعتماد داده بین سرویس‌ها توضیح می‌دهد.

## معنی «ریل‌تایم» در سیستم

برای مشتری، صفحه ابتدا داده‌ی معتبر را از REST می‌گیرد و سپس WebSocket تغییرات جدید را به آن می‌رساند. اگر اتصال قطع شد، رابط وضعیت آخرین همگام‌سازی را نشان می‌دهد و پس از وصل‌شدن دوباره، داده را از سرور تازه‌سازی می‌کند.

WebSocket را برای پیام و به‌روزرسانی زنده استفاده کن؛ آن را منبع اصلی داده یا جایگزین API نکن. Gateway باید فقط رویدادهایی را به کاربر، خانواده یا شعبه برساند که مجوز دیدنشان را دارد. در استقرار چند نمونه‌ای Gateway، آن نمونه‌ها نیز از NATS رویداد می‌گیرند تا اتصال کاربر به هر نمونه‌ای باشد، به‌روزرسانی را دریافت کند.

یک هدف آزمایشی برای پایلوت می‌تواند نمایش رویدادهای داخلی در کمتر از یک ثانیه در صدک ۹۵ باشد. زمان سامانه‌ی کارت، کیفیت اینترنت شعبه و سرویس بیرونی باید جدا سنجیده شوند؛ زمان پاسخ دستگاه بیرونی را نمی‌توان با معماری داخلی تضمین کرد.

## استثنای مهم: پول و مصرف اعتبار

ماژول‌ها می‌توانند مستقل باشند، اما اعتبار کیف پول باید داخل **سرویس مالک کیف پول** اتمیک و قابل‌اعتماد تغییر کند. بین پرداخت و شارژ کیف پول، معمولاً یک جریان رویدادی با وضعیت‌هایی مثل «در انتظار»، «تأییدشده» و «ثبت‌شده» لازم است؛ رابط می‌تواند در این فاصله وضعیت را زنده نشان دهد.

برای مصرف کارت در دستگاه هم باید منبع حقیقت مشخص باشد. در شروع، اگر سامانه‌ی فعلی RFID مصرف را تأیید و ثبت می‌کند، همان سامانه منبع حقیقت مصرف بماند و سرویس اتصال فانتینو رویداد را منتشر کند. اگر بعداً خود Wallet فانتینو قرار است اجازه‌ی خرج‌کردن بدهد، دستگاه باید پاسخ تأیید را در لحظه بگیرد یا در شعبه سازوکار محلی و همگام‌سازی طراحی شود؛ در این عملیات، یک نقطه‌ی هماهنگی فنی وجود خواهد داشت.

## تغییرهای اصلی نسبت به پیشنهاد قبلی

- بک‌اند از ماژولار یکپارچه به **سرویس‌های مستقل NestJS** تغییر می‌کند.
- **NATS JetStream** پیام‌رسان اصلی رویدادهای بین سرویس‌ها می‌شود.
- **WebSocket Gateway** برای به‌روزرسانی زنده‌ی وب‌اپ اضافه می‌شود.
- Redis فقط برای cache و موارد مشابه می‌ماند؛ BullMQ دیگر پیام‌رسان اصلی سیستم نیست.
- PostgreSQL حفظ می‌شود، ولی مالکیت داده و migration برای هر سرویس جداست.
- TypeScript همچنان برای Next.js و NestJS کافی است؛ زبان دیگری لازم نیست. در صورت نیاز به agent محلی کنار تجهیزات یا پروتکل خاص دستگاه، Go را بعداً بررسی کن.
- Kafka را زمانی بررسی کن که حجم رویدادها، نیاز به نگهداری و بازپخش طولانی‌مدت، یا تحلیل جریانی واقعاً آن را توجیه کند. Kafka برای جریان‌های پرتعداد و پایدار طراحی شده است؛ برای شروع فانتینو، NATS JetStream انتخاب سبک‌تری برای رویدادهای زنده و مستقل است.

بنابراین از روز اول **قرارداد رویداد، مالکیت جداگانه‌ی داده، Outbox، مصرف‌کننده‌ی idempotent و WebSocket Gateway** را جزو طراحی بگذار. این‌ها شرط واقعی مستقل‌بودن سرویس‌ها و زنده‌بودن تجربه‌ی مشتری هستند.
